# Домашнее задание к занятию «Микросервисы: масштабирование»

## Задача 1: Кластеризация

Для построения отказоустойчивой микросервисной платформы выбран стек на базе оркестратора **Kubernetes**. Инфраструктура дополняется компонентами **Ingress NGINX**, **Metrics Server**, **KEDA** и **HashiCorp Vault**. Данная связка полностью закрывает заявленные требования.

### Реализация требований технического задания:

1. **Поддержка контейнеров:**
   Среда выполнения containerd внутри Kubernetes запускает любые OCI-совместимые образы. Оркестратор контролирует жизненный цикл подов, автоматически перезапускает упавшие контейнеры и распределяет нагрузку по физическим или виртуальным нодам.

2. **Обнаружение сервисов и маршрутизация запросов:**
   Встроенный DNS-сервис CoreDNS отвечает за Service Discovery внутри кластера. Микросервисы связываются друг с другом по доменным именам формата `<service-name>.<namespace>.svc.cluster.local`. Балансировку трафика между репликами выполняет Kube-Proxy и абстракция Service (тип ClusterIP).

3. **Горизонтальное масштабирование:**
   Контроллеры Deployment и ReplicaSet позволяют изменять количество реплик сервиса на лету. Достаточно выполнить команду `kubectl scale` или изменить значение поля `replicas` в манифесте приложения.

4. **Автоматическое масштабирование:**
   Горизонтальное автомасштабирование подов возложено на Horizontal Pod Autoscaler (HPA). Он считывает метрики потребления CPU и RAM через Metrics Server. При росте нагрузки HPA поднимает новые поды, а при спаде - плавно гасит лишние. Если требуется реакция на длину очередей сообщений (RabbitMQ, Kafka), подключается оператор KEDA. Для добавления самих нод в кластер при нехватке вычислительных мощностей используется Cluster Autoscaler.

5. **Разделение ресурсов (внешний и внутренний контур):**
   Внутренние сервисы изолированы внутри сети кластера и доступны только по внутренним IP-адресам (Service ClusterIP). Сетевой доступ между подами разграничивают политики NetworkPolicy. Внешний трафик поступает строго через единую точку входа - Ingress Controller (или API Gateway), подключенный к облачному LoadBalancer. Контроллер терминирует SSL/TLS и проксирует запросы только к тем сервисам, которые явно опубликованы через правила Ingress.

6. **Конфигурирование и безопасное хранение секретов:**
   Нечувствительные параметры передаются в контейнеры через ConfigMap в виде переменных окружения или примонтированных файлов конфигураций. Секретные данные (пароли к базам данных, API-ключи, сертификаты) хранятся в защищенном хранилище HashiCorp Vault. В поды они доставляются через External Secrets Operator или Vault CSI Provider, что исключает хранение открытых секретов в репозиториях кода и Git-коммитах.

### Обоснование выбора:
Kubernetes - общепринятый стандарт индустрии для микросервисных архитектур. Он решает проблемы высокой доступности, гибкого масштабирования и самовосстановления приложений без привязки к конкретному провайдеру (отсутствует vendor lock-in). Решение доступно как в виде самостоятельной установки, так и в формате Managed Service у большинства облачных провайдеров.

## Задача 2: Распределённый кеш

Для организации распределенного хранения сессий развернут Redis Cluster, состоящий из трех шард (мастеров) и трех реплик. Стенд поднят с помощью Docker Compose в изолированной bridge-сети с фиксированной адресацией.

Конфигурация стенда вынесена в отдельный файл [docker-compose.yaml](./docker-compose.yaml).

Запуск контейнеров выполнен командой:

```bash
docker compose up -d
```

### Инициализация кластера

Объединение узлов в кластер выполнено с помощью встроенной утилиты `redis-cli`:

```bash
docker exec -it redis-node-1 redis-cli --cluster create \
  172.28.0.11:6379 \
  172.28.0.12:6379 \
  172.28.0.13:6379 \
  172.28.0.14:6379 \
  172.28.0.15:6379 \
  172.28.0.16:6379 \
  --cluster-replicas 1 \
  --cluster-yes
```

Утилита автоматически выделила три мастера и привязала к каждому по одной реплике:

### Проверка состояния и топологии

Проверка общего состояния кластера командой `cluster info`:

```bash
docker exec -it redis-node-1 redis-cli cluster info
```

Вывод подтверждает готовность кластера (`cluster_state:ok`) и наличие 6 активных узлов (`cluster_known_nodes:6`):
