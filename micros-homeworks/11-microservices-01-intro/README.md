# Домашнее задание к занятию «Введение в микросервисы»

## Задача

Руководство крупного интернет-магазина, у которого постоянно растет пользовательская база и количество заказов, рассматривает возможность переделки своей внутренней ИТ-системы на основе микросервисов. 

Вас пригласили в качестве консультанта для оценки целесообразности перехода на микросервисную архитектуру. 

Опишите, какие выгоды может получить компания от перехода на микросервисную архитектуру и какие проблемы нужно решить в первую очередь.

---

### Решение

Переход крупного интернет-магазина с монолитной архитектуры на микросервисную оправдан при активном росте базы клиентов и операций. Монолитные решения на этапе масштабирования упираются в пределы вертикального роста серверов и создают организационные барьеры между отделами. Ниже приведена детальная оценка выгод и первоочередных инженерных вызовов.

---

#### 1. Выгоды от перехода на микросервисную архитектуру

1. **Изолированное масштабирование компонентов под неравномерную нагрузку**  
   В интернет-магазине профиль нагрузки сильно варьируется. Поиск и просмотр каталога генерируют в десятки раз больше трафика, чем создание корзины и оформление заказа. В монолите приходится поднимать тяжелые копии всего приложения целиком. Микросервисы позволяют независимо масштабировать только высоконагруженные домены (каталог, поисковый движок, авторизацию), экономя серверные мощности и бюджет на инфраструктуру.

2. **Отказоустойчивость и локализация аварий**  
   Падение второстепенного модуля в монолите (например, генератора персональных рекомендаций или сервиса отзывов) способно уложить весь веб-сайт. Микросервисы локализуют сбои. Паттерны переборки (Bulkhead) и прерывателя цепи (Circuit Breaker) сохраняют работоспособность критического пути - пользователь сможет положить товар в корзину и оплатить заказ, даже если сервис рекомендаций временно недоступен.

3. **Сокращение Time-to-Market и повышение частоты выкладок**  
   Маленький изолированный сервис компилируется, тестируется и выкатывается за считанные минуты. Нет нужды согласовывать глобальный релизный поезд со всеми разработчиками монолита. Команды деплоят функционал автономно по несколько раз в день, быстро доставляя маркетинговые гипотезы до клиентов.

4. **Оптимизация командной структуры по закону Конвея**  
   Архитектура отражает структуру коммуникаций организации. Система делится на домены (каталог, склад, биллинг, логистика), за каждым закрепляется компактная кросс-функциональная команда полного цикла (разработка, тестирование, эксплуатация). Это снижает коммуникационные накладные расходы и повышает ответственность за продукт.

5. **Свобода выбора технологического стека под конкретную задачу**  
   Инженерам не навязывается один общий язык или фреймворк. Высоконагруженный шлюз и стриминг данных реализуются на Go, рекомендательные алгоритмы и обработка данных - на Python, а учет складских остатков и финансовые транзакции - на Java или .NET с реляционными СУБД.

---

#### 2. Проблемы и первоочередные задачи перехода

Микросервисы не решают внутренние проблемы плохого кода автоматически. Они переносят сложность из кодовой базы в инфраструктуру и межсервисные коммуникации. Перед началом распила монолита компании необходимо закрыть ключевые технологические и платформенные пробелы.

1. **Создание платформы наблюдаемости (Observability)**  
   Диагностика распределенной системы вслепую невозможна. В первую очередь разворачиваются три кита мониторинга:
   - Централизованный сбор логов (OpenSearch / ELK / Vector + Loki) с обязательным единым Correlation ID для каждого запроса.
   - Сквозная трассировка (Jaeger / OpenTelemetry), наглядно показывающая задержки и путь запроса через цепочки микросервисов.
   - Мониторинг метрик и алертинг (Prometheus + Grafana) для отслеживания Golden Signals (латентность, ошибки, трафик, насыщение).

2. **Отказ от распределенных транзакций и переход на Event-driven архитектуру**  
   Попытка сохранить строгую транзакционность (ACID) между базами данных микросервисов приведет к блокировкам и медленной работе. Первоочередная задача - спроектировать базы данных по принципу «Database-per-service» и перейти на модель согласованности в конечном счете (Eventual Consistency). Для координации бизнес-процессов (оплата -> бронирование на складе -> доставка) внедряются брокеры очередей (Apache Kafka, RabbitMQ) и паттерны оркестрации/хореографии (Saga, Outbox pattern).

3. **Стандартизация CI/CD и платформенной инфраструктуры**  
   Ручной деплой сотен сервисов исключен. Необходима платформа оркестрации контейнеров (Kubernetes), единые пайплайны сборки/тестирования (GitLab CI, GitHub Actions), централизованные реестры артефактов и версионирование конфигураций (HashiCorp Vault, Spring Cloud Config, Kubernetes Secrets).

4. **Проектирование API и обеспечение обратной совместимости**  
   Изменение контракта одним сервисом не должно ломать соседние зависимости. Требуется внедрить строгие стандарты описания API (OpenAPI, protobuf), семантическое версионирование интерфейсов, а также развернуть API Gateway для централизованной маршрутизации, rate limiting и первичной валидации клиентских запросов.

5. **Безопасность сетевого контура**  
   Модель «доверяем всему внутри периметра» в микросервисах небезопасна. Необходимо сразу внедрить механизмы взаимной аутентификации (mTLS / Service Mesh) между компонентами и токены доступа (OAuth2 / JWT) для авторизации запросов пользователей.

6. **Исключение антипаттернов декомпозиции**  
   Нельзя начинать деление на микросервисы вслепую:
   - *Антипаттерн «Серебряная пуля»:* ожидание, что микросервисы сами по себе решат проблемы бизнеса.
   - *Антипаттерн «Наносервисы»:* дробление кода на микроскопические функции из 50 строк. Это перегружает сеть и усложняет эксплуатацию. Границы сервисов должны строиться строго вокруг контекстов предметной области (Bounded Contexts по методологии DDD).
   - Распил должен идти поэтапно по паттерну «Душитель» (Strangler Fig), когда от монолита постепенно отделяют изолированные модули, а не переписывают систему с нуля.

---

### Резюме консультанта

Переход на микросервисы для растущего интернет-магазина экономически и технически оправдан - он разблокирует горизонтальное масштабирование и ускорит релизный цикл команд. Однако миграцию следует начинать не с переписывания кода, а с подготовки фундамента - развертывания платформы оркестрации, внедрения систем мониторинга/трейсинга и согласования доменных границ команд.
