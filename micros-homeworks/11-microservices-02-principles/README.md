### Задание 1. API Gateway

Для выбора шлюза API рассмотрены четыре востребованных решения: NGINX, Kong, Traefik и Envoy.

#### Сравнительная таблица решений

| Критерий | NGINX | Kong Gateway | Traefik | Envoy |
| :--- | :--- | :--- | :--- | :--- |
| **Маршрутизация по конфигурации** | Конфигурационные файлы (`nginx.conf`), директивы `location`, rewrite-правила, map. | Декларативная конфигурация (YAML) либо REST API управления. | Автоматический discovery (Docker, K8s, Consul), статические и динамические правила. | Сложные YAML/JSON описания, динамический xDS API. |
| **Проверка аутентификации** | Модуль `ngx_http_auth_request_module` (субзапросы к auth-сервису), HTTP Basic Auth, JWT (в NGINX Plus). | Богатая база готовых плагинов: JWT, OAuth 2.0, Key Authentication, OIDC. | Middleware-цепочки: ForwardAuth, BasicAuth, кастомные плагины. | Фильтр `envoy.filters.http.ext_authz` (gRPC/HTTP), встроенный парсер JWT. |
| **Терминация HTTPS** | Модуль `ngx_http_ssl_module`, тонкая настройка шифров, OCSP stapling, HTTP/2 и HTTP/3. | Нативная поддержка SSL/TLS, управление сертификатами через API или плагины. | Встроенная автоматическая генерация и ротация сертификатов Let's Encrypt. | Гибкие TLS-контексты, ротация сертификатов без перезагрузки через SDS. |
| **Сложность внедрения и поддержки** | Низкая. Понятный синтаксис директив, колоссальная база документации. | Средняя. Требует понимания сущностей сервисов, маршрутов и плагинов. | Низкая. Практически нулевая конфигурация при работе с Docker-метками. | Высокая. Длинная кривая обучения, многоуровневые конфигурации. |
| **Потребление ресурсов и производительность** | Высочайшая скорость работы на C, минимальное потребление RAM и CPU. | Высокая производительность OpenResty/Lua, небольшой оверхед на плагины. | Хорошая скорость на Go, потребление ресурсов выше вариантов на C/C++. | Экстремальная скорость на C++, оптимизирован под высокие нагрузки. |

#### Обоснование выбора

Для проектируемой инфраструктуры выбран **NGINX** (как классический надежный шлюз) с возможностью расширения до **Kong** при росте числа сервисов.

Причины выбора NGINX:
1. **Маршрутизация.** NGINX эффективно скрывает топологию внутренней сети. Внешние клиенты работают с единым доменным именем. Запросы перенаправляются по внутренним именам контейнеров через директивы `proxy_pass`.
2. **Аутентификация.** Механизм `auth_request` позволяет выполнять субзапрос к независимому сервису безопасности перед передачей трафика в бизнес-сервисы. Если токен валиден (код 200), NGINX пускает запрос дальше. Если токен просрочен или отсутствует, шлюз возвращает 401/403. Логика проверки авторизации централизована и не дублируется в каждом микросервисе.
3. **Терминация HTTPS.** Криптографическая нагрузка снимается с сервисов приложений. Сертификаты и закрытые ключи хранятся и ротируются централизованно в одном месте. Внутри защищенной сети контейнеров трафик идет по легковесному протоколу HTTP.
4. **Надежность и простота.** NGINX требует минимум оперативной памяти. Синтаксис конфигурации понятен любому инженеру поддержки. В системе отсутствуют лишние базы данных метаданных, что снижает число точек отказа.

### Задание 2. Брокер сообщений

В рамках проектирования межсервисного асинхронного взаимодействия сопоставлены ключевые брокеры сообщений: RabbitMQ, Apache Kafka, NATS JetStream и Apache Pulsar.

#### Сравнительная таблица брокеров сообщений

| Критерий | RabbitMQ | Apache Kafka | NATS JetStream | Apache Pulsar |
| :--- | :--- | :--- | :--- | :--- |
| **Кластеризация и надежность** | Встроенная кластеризация. Кворумные очереди (Quorum Queues) работают на алгоритме Raft. Высокая отказоустойчивость. | Распределенная архитектура. Репликация партиций. Механизм KRaft гарантирует консенсус узлов. | Встроенный Raft-кластер. Автоматический выбор лидера и репликация стейта. | Двухуровневая модель. Брокеры работают отдельно от хранилища (Apache BookKeeper). |
| **Хранение на диске** | Поддерживает сохранение на диск (persistent delivery mode, кворумные очереди пишут лог на диск). | Append-only commit log на диске. Сообщения хранятся заданное время (retention). | Поддерживает запись потоков в память либо на диск с гибкой политикой очистки. | Запись всех данных в сегменты BookKeeper на диск с распределенной репликацией. |
| **Скорость работы (throughput)** | Десятки тысяч сообщений в секунду на узел. Низкая задержка передачи сообщений (sub-millisecond). | Миллионы сообщений в секунду за счет последовательного чтения/записи и page cache ОС. | Сотни тысяч сообщений в секунду при микросекундных задержках. | Высокая пропускная способность при строгом разделении чтения и записи. |
| **Форматы сообщений** | Payload-agnostic. Передает сырые байты: JSON, Protobuf, Avro, XML или бинарный контент. | Payload-agnostic. Байт-массив. Доступна валидация схем через Schema Registry. | Payload-agnostic. Принимает любые бинарные форматы и структурированные данные. | Payload-agnostic. Встроена схема управления сообщениями (Schema Registry). |
| **Разделение прав доступа (ACL)** | Разделение через Virtual Hosts (vhosts). Гибкие regex-права на операции read, write, configure. | Детальные списки ACL на топики и группы консьюмеров через SASL, Kerberos или mTLS. | Разделение доступа по топикам через токены, JWT-ключи и nkeys учетных записей. | Ролевой доступ (RBAC) на уровне тенантов, неймспейсов и топиков. |
| **Простота эксплуатации** | Простая. Встроенный Web UI для управления очередями, легкая настройка, стандартный плагин Prometheus. | Высокая сложность. Требует глубокого тюнинга JVM, дисковой подсистемы и управления партициями. | Очень простая. Один бинарный файл на Go, минимальное потребление ресурсов, нет JVM. | Экстремально высокая. Требует отдельного администрирования ZooKeeper, BookKeeper и брокеров. |

#### Обоснование выбора

Для разрабатываемой микросервисной системы выбран **RabbitMQ** (с использованием кворумных очередей).

Факторы выбора:
1. **Баланс производительности и поддержки.** Скорости RabbitMQ с запасом хватает для сервисных очередей задач, событий создания пользователей и очередей обработки файлов. При этом брокер не требует выделения команд для тюнинга JVM.
2. **Простота управления.** Полнофункциональный Web UI идет в базовом дистрибутиве. Оператор визуально видит объемы очередей, консьюмеров и факт доставки сообщений. Метрики легко забираются в Prometheus без внешних агентов.
3. **Надежность доставки.** Использование Quorum Queues решает проблему split-brain при сетевых авариях. Сообщения сохраняются на диск. Подтверждения доставки (acknowledgements) исключают потерю данных при падении сервисов-обработчиков.
4. **Контроль прав и изоляция.** Механизм виртуальных хостов (vhosts) позволяет изолировать контуры (например, stage и prod) внутри одного кластера. Права сервисов жестко ограничиваются регулярными выражениями на конкретные exchange и queue.
5. **Универсальность форматов.** Брокер принимает любые полезные нагрузки, будь то бинарный payload сжатых изображений или служебный JSON событий авторизации.

### Задание 3*. Реализация API Gateway на NGINX (Docker Compose)

Стек состоит из трех сервисов и шлюза:
- `storage` (MinIO) - хранилище изображений, бакет `images`.
- `uploader` (Node.js) - валидация типа файла и выгрузка в S3.
- `security` (Python / Flask) - выдача и проверка JWT-токенов.
- `gateway` (NGINX) - единая входная точка, маршрутизация и авторизация запросов через директиву `auth_request`.

#### Особенности настройки окружения

В исходных файлах проекта внесены точечные изменения:
1. **Реестр образов MinIO.** В связи с закрытием публичного доступа к репозиториям `minio/minio` на Docker Hub и Quay.io применены образы `cgr.dev/chainguard/minio` и `cgr.dev/chainguard/minio-client`.
2. **Инициализация бакета.** В контейнер `createbuckets` добавлен цикл ожидания готовности MinIO, создание целевого бакета `images` и выдача прав на чтение через `mc anonymous set download`.
3. **Совместимость Flask и Jinja2.** В сервисе `security` зафиксированы совместимые версии пакетов (`Flask==2.0.3`, `Werkzeug==2.0.3`, `Jinja2==3.0.3`) на базе `python:3.9-slim`. В обработчик валидации токена добавлены явные возвраты статуса HTTP 401 для исключений `ExpiredSignatureError` и `InvalidTokenError`.
4. **Конфигурация NGINX.** В `gateway/nginx.conf` настроен внутренний субзапрос `/_auth_verify` на эндпоинт `/v1/token/validation` сервиса `security`. Публичные пути (`/token`, `/v1/token`, `/v1/register`) открыты для всех клиентов, а запросы к `/upload`, `/v1/upload` и `/v1/user` защищены директивой `auth_request`.

#### Сборка и запуск стека

Запуск всех сервисов в фоновом режиме:

```bash
docker compose up -d --build
docker compose ps
```

#### Тестирование маршрутизации и безопасности

Для проверки сценариев создаем тестовый файл JPEG с валидным заголовком, запрашиваем JWT-токен, загружаем файл через шлюз, скачиваем его из MinIO и тестируем отказ в доступе без токена:

```bash
# Создание тестового JPEG-изображения
echo "/9j/4AAQSkZJRgABAQEASABIAAD/2wBDAP//////////////////////////////////////////////////////////////////////////////////////wgALCAABAAEBAREA/8QAFBABAAAAAAAAAAAAAAAAAAAAAP/aAAgBAQABPxA=" | base64 -d > test.jpg

# Получение JWT токена пользователя bob (анонимный доступ)
TOKEN=$(curl -s -X POST -H 'Content-Type: application/json' -d '{"login":"bob", "password":"qwe123"}' http://localhost/token)
echo "JWT Token: $TOKEN"

# Загрузка файла через шлюз с токеном (проверка auth_request)
UPLOAD_RES=$(curl -s -X POST -H "Authorization: Bearer $TOKEN" -H 'Content-Type: octet/stream' --data-binary @test.jpg http://localhost/upload)
echo "Upload result: $UPLOAD_RES"

# Получение имени файла и скачивание из MinIO через NGINX
FILENAME=$(echo "$UPLOAD_RES" | grep -oE '[a-f0-9\-]+\.jpg')
curl -s -I http://localhost/images/$FILENAME | head -n 5

# Проверка ограничения доступа без токена
curl -i -X POST -H 'Content-Type: octet/stream' --data-binary @test.jpg http://localhost/upload | head -n 5
```
