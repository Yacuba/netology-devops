### Задание 1

Для такой платформы мониторинг стоит разделить на три понятные части - HTTP-интерфейс, ресурсы сервера и метрики самого приложения.

Сначала закрываем веб-уровень:
Смотрим на частоту запросов (RPS), время обработки (перцентили p95 и p99) и распределение кодов ответов. Ошибки 5xx сразу укажут на сбои бэкенда или падение вычислительных скриптов. Перцентили вместо среднего времени помогут вовремя заметить задержки у отдельных пользователей.

Дальше оцениваем ресурсы хоста, где главный фокус идет на CPU и диск:
1. Процессор. Отслеживаем Load Average и распределение утилизации ядер (user, system, iowait). Платформа проводит расчеты, поэтому процессор станет главным узким местом. Метрика iowait покажет, если ядра начнут простаивать в ожидании дисковых операций.
2. Диск. Контролируем не только свободные гигабайты, но и остаток индексных дескрипторов (inodes через `df -i`). Текстовые отчеты обычно генерируют массу мелких файлов. Свободное место еще останется, а иноды кончатся, из-за чего система откажется сохранять новые отчеты с ошибкой `No space left on device`. Параллельно смотрим на IOPS и задержки записи.
3. Память. Мониторим объем свободной RAM и использование swap. Если вычисления вытеснят данные в своп, скорость работы сервиса упадет почти до нуля.

На уровне самого сервиса забираем две вещи - глубину очереди задач и время сборки одного отчета. Если очередь на вычисления стабильно растет, воркеры не справляются с потоком и пора масштабировать платформу.

### Задание 2

Продакт-менеджеру не нужны системные счетчики вроде CPU LA или свободных инодов. Бизнесу важно знать два параметра - доступен ли сервис и насколько быстро клиенты получают готовые отчеты.

Вместо графиков утилизации ресурсов предлагаем менеджеру понятную SRE-модель на базе SLI, SLO и SLA:

1. **SLI (Service Level Indicator)** - метрики качества, которые напрямую ощущает пользователь. Сюда берем процент успешных HTTP-ответов без 5xx кодов, долю запросов с временем ответа быстрее 1-2 секунд и процент отчетов, рассчитанных без ошибок.
2. **SLO (Service Level Objective)** - внутренняя цель команды по надежности. Например, держим планку 99.5% всех отчетов за месяц должны формироваться успешно и укладываться в заданный тайминг.
3. **SLA (Service Level Agreement)** - внешние обязательства перед клиентами с финансовой ответственностью. Планку SLA всегда ставят чуть ниже SLO (например, 99.0%), чтобы у команды оставался зазор на внештатные ситуации до наступления штрафов.

Для наглядного контроля внедряем концепцию **бюджета ошибок (Error Budget)**. Это допустимый процент сбоев за отчетный период (для SLO 99.5% бюджет равен 0.5%). Пока бюджет не исчерпан, продакт может спокойно выпускать новые фичи. Если сбоев стало слишком много и бюджет тает, релизы замораживаются, а команда переключается на стабилизацию платформы.

Для самого менеджера выводим отдельный верхнеуровневый дашборд. На нем отображаем текущий процент выполнения SLO, статус доступности сервиса и остаток бюджета ошибок в виде понятных индикаторов.

### Задание 3

Разработчикам нужны не терабайты сырых логов, а контекст ошибок - трейсы исключений, параметры запросов и частота падений. При нулевом бюджете задачу закрываем бесплатными инструментами на имеющихся мощностях.

Рабочие варианты решений:

1. **Self-hosted Sentry.** Оптимальный инструмент для трекинга ошибок приложений. Полностью бесплатный опенсорс, быстро поднимается через Docker Compose. SDK подключается в код в пару строк. Sentry агрегирует повторяющиеся ошибки, хранит стек вызовов, переменные окружения и умеет отправлять нотификации в Telegram или Slack.

2. **Стек Grafana Loki + Promtail.** Если разработчикам нужен доступ ко всему потоку логов, а не только к фатальным сбоям. Loki потребляет значительно меньше ресурсов, чем Elasticsearch, так как индексирует только метаданные (лейблы), а не сам текст. Просматривать логи можно через бесплатную Grafana.

3. **Сбор ошибок через Vector или Fluent Bit в чат команды.** Легковесный агент ставится на хост, читает stdout контейнеров или файлы логов, фильтрует события по уровню `ERROR` или кодам `5xx` и через webhook отсылает сообщения в рабочий мессенджер. 

4. **Ограниченный прямой доступ к логам.** Если свободных мощностей нет вообще, настраиваем утилиту `logrotate` для сжатия старых файлов и выдаем разработчикам read-only доступ на чтение каталогов с логами либо права на просмотр `docker logs` и `journalctl`.

### Задание 4

Ошибка заключается в том, что формула полностью игнорирует ответы группы **3xx** (перенаправления и кеширование), а также возможные **1xx** (информационные).

В знаменателе `summ_all_requests` суммируются все без исключения ответы: `1xx + 2xx + 3xx + 4xx + 5xx`. 

Если в системе отсутствуют коды 4xx и 5xx, а формула дает только 70%, значит, оставшиеся 30% трафика составляют ответы **3xx**. Это штатные ответы сервиса:
- Редиректы `301` или `302` (перенаправление на HTTPS или авторизацию).
- Ответ `304 Not Modified`, который сообщает клиенту, что контент в кэше актуален и повторно скачивать его не нужно.

Такие ответы не считаются сбоями. Исключив их из числителя, мы занизили реальную доступность системы.

Для исправления ситуации формулу приводят к виду:

```text
(summ_2xx_requests + summ_3xx_requests) / summ_all_requests
```

Если же цель SLA - отслеживать именно отказоустойчивость сервиса (без учета клиентских ошибок), надежнее считать долю запросов без серверных сбоев:

```text
(summ_all_requests - summ_5xx_requests) / summ_all_requests
```

### Задание 5

Выбор между Pull и Push моделями определяет требования к сети, безопасность и способ обнаружения сервисов.

#### Pull-модель (сервер опрашивает узлы)

Сервер мониторинга по расписанию подключается к эндпоинтам агентов или сервисов и забирает свежие данные (типичный пример - Prometheus).

**Плюсы:**
- Централизованное управление. Сервер сам задает частоту опроса и таймауты. При росте нагрузки можно централизованно уменьшить интервалы сбора в одной конфигурации.
- Четкий контроль доступности узлов. Если сервер не смог достучаться до эндпоинта по таймауту, он сразу фиксирует статус отказа (например, метрика `up == 0`).
- Простая ручная проверка. Работу агента и формат выдачи метрик легко протестировать через обычный `curl` в консоли.
- Безопасность инфраструктуры. Агентам на целевых серверах не нужны учетные данные и сетевые доступы к центральной базе мониторинга.

**Минусы:**
- Проблемы с NAT и динамическими IP. Сервер обязан иметь прямой маршрут до каждого клиента. Если сервисы закрыты частными сетями или меняют адреса, приходится ставить прокси и VPN-туннели.
- Сложность работы с короткоживущими задачами (Cron, Serverless/Lambda). Процесс может завершиться быстрее, чем наступит следующий цикл опроса сервера.

#### Push-модель (клиенты шлют данные на сервер)

Агенты или компоненты приложения сами генерируют пакеты с метриками и отправляют их на центральный шлюз (пример - Telegraf, StatsD).

**Плюсы:**
- Легкое прохождение через NAT и строгие фаерволы. Для отправки нужен только исходящий доступ от агента к единому IP/домену сборщика.
- Подходит для разовых и динамических задач. Скрипт отправляет результат работы сразу в момент завершения и гасится.
- Высокая скорость и низкие задержки. Метрики можно гнать потоком по легковесному протоколу UDP без ожидания ответа от базы.
- Репликация потоков. Локальный агент может дублировать метрики параллельно в несколько независимых баз данных.

**Минусы:**
- Опасность перегрузки приемника (DDoS). При массовом рестарте сервисов или сетевом сбое агенты могут одновременно завалить сервер мониторинга ретраями. Для защиты приходится ставить буферы вроде Apache Kafka.
- Неочевидный статус хоста. Если метрики перестали приходить, сервер не знает причину: упала вся машина, завис агент или просто нет данных для отправки. Приходится отдельно настраивать детекторы тишины (Deadman checks).
- Децентрализация настроек. Интервалы отправки и список метрик зашиты в конфигурациях самих агентов на хостах.

### Задание 6

Классификация систем по модели сбора данных:

- **Prometheus - Pull.** Базовая схема работы построена на регулярном опросе эндпоинтов сервисов по HTTP. Для кратковременных задач можно подключить промежуточный компонент Pushgateway, но сам Prometheus все равно забирает из него метрики методом Pull.
- **TICK - Push.** Агент Telegraf собирает системные показатели и пакетно выталкивает их в базу данных InfluxDB.
- **Zabbix - Гибридная.** Поддерживает оба сценария. В пассивном режиме (Zabbix Agent Passive) сервер сам обращается к агенту за данными (Pull). В активном режиме (Zabbix Agent Active) агент сам собирает метрики и отправляет их на сервер или прокси (Push).
- **VictoriaMetrics - Гибридная.** Утилита `vmagent` умеет самостоятельно собирать метрики по расписанию (Pull-модель, совместимая с Prometheus). Одновременно с этим ядро базы нативно принимает метрики через протоколы Prometheus remote_write, InfluxDB line protocol и Graphite (Push-модель).
- **Nagios - Pull.** Центральный сервер по расписанию запускает проверки удаленных узлов через демоны вроде NRPE (Nagios Remote Plugin Executor). Для реализации Push-модели требуется подключать отдельный сервис пассивных проверок NSCA.

### Задание 9

Для мониторинга Docker-окружения подключен плагин `inputs.docker`. 

В конфигурационном файле `telegraf/telegraf.conf` настроена секция сбора данных с сокета демона:

```toml
[[inputs.docker]]
  endpoint = "unix:///var/run/docker.sock"
  container_name_include = []
  container_name_exclude = []
  timeout = "5s"
  gather_services = false
```

В манифесте `docker-compose.yml` в сервис `telegraf` добавлен проброс Unix-сокета и привилегированный режим:

```yaml
  telegraf:
    build:
      context: ./images/telegraf/
      dockerfile: ./${TYPE}/Dockerfile
      args:
        TELEGRAF_TAG: ${TELEGRAF_TAG}
    image: "telegraf"
    user: root
    privileged: true
    environment:
      HOSTNAME: "telegraf-getting-started"
    links:
      - influxdb
    ports:
      - "8092:8092/udp"
      - "8094:8094"
      - "8125:8125/udp"
    volumes:
      - ./telegraf/:/etc/telegraf/
      - /var/run/docker.sock:/var/run/docker.sock
    depends_on:
      - influxdb
```

Для предоставления доступа непривилегированному пользователю внутри контейнера к сокету хоста применены права: `sudo chmod 666 /var/run/docker.sock`.

После перезапуска агента Telegraf в базе данных `telegraf.autogen` зарегистрированы группы измерений контейнеров:
- `docker`
- `docker_container_blkio`
