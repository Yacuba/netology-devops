# Домашнее задание к занятию «Микросервисы: подходы»

## Задача 1: Обеспечить разработку

### Предложенное решение

Для организации процессов разработки, тестирования и непрерывной доставки выбран облачный сервис **GitLab (GitLab.com SaaS)** в связке с собственными агентами сборки **GitLab Runner (Self-hosted)**.

Схема взаимодействия компонентов:
1. Исходный код микросервисов хранится в изолированных репозиториях внутри единой группы проектов компании в GitLab.
2. При событиях в Git (push, merge request, теги) GitLab CI запускает пайплайн по описанию в файле `.gitlab-ci.yml`.
3. Управляющий сервер GitLab SaaS передает задачи на сборку агентам GitLab Runner, развернутым на собственных серверах (on-premise / Yandex Cloud).
4. Агенты скачивают кастомные docker-образы для сборки, выполняют компиляцию, прогон тестов и упаковку готовых контейнеров.
5. Готовые образы пушатся во встроенный GitLab Container Registry.

### Соответствие требованиям

| Требование ТЗ | Реализация в GitLab |
|---|---|
| Облачная система | Использование GitLab.com (SaaS). Не требует поддержки собственного сервера управления. |
| Система контроля версий Git | GitLab построен на базе Git. Поддерживает полный Git-flow и Merge Requests. |
| Репозиторий на каждый сервис | Структура GitLab Groups / Subgroups позволяет вести отдельный репозиторий под каждый сервис. |
| Запуск сборки по событию из Git | Триггеры `on: push`, `rules`, вебхуки и запуск по созданию Merge Request. |
| Запуск сборки по кнопке с параметрами | Раздел CI/CD -> Pipelines -> «Run pipeline». Переменные задаются через веб-интерфейс перед стартом. |
| Привязка настроек к каждой сборке | Секция `variables` на уровне отдельных job или передача параметров во время ручного запуска. |
| Шаблоны конфигураций сборок | Директива `include` (`local`, `file`, `template`, `remote`). Позволяет выносить пайплайны в базовый репозиторий. |
| Безопасное хранение секретов | Встроенный механизм CI/CD Variables с флагами Masked и Protected. Доступна нативная интеграция с HashiCorp Vault. |
| Несколько конфигураций сборок из одного репозитория | Использование нескольких файлов пайплайнов через `trigger:include` либо разделение логики через блок `rules`. |
| Кастомные шаги при сборке | Секции `before_script`, `script`, `after_script` с любыми sh/bash-командами. |
| Собственные докер-образы для сборки | Директива `image:` на уровне пайплайна или джобы. Указывает любой образ из публичного или приватного реестра. |
| Развертывание агентов на собственных серверах | Установка `gitlab-runner` на свои виртуальные машины или Kubernetes с регистрацией по токену. |
| Параллельный запуск нескольких сборок | Обеспечивается параметром `concurrent` в конфигурации `config.toml` раннера и пулом доступных агентов. |
| Параллельный запуск тестов | Директива `parallel:` для разделения тестов на N параллельных потоков либо запуск матричных сборок (`parallel:matrix`). |

### Обоснование выбора

GitLab SaaS закрывает весь цикл разработки микросервисной системы в рамках одного продукта. Решение избавляет команду от необходимости поддерживать и обновлять центральный сервер автоматизации.

Вынос агентов сборки (Runners) на собственные мощности исключает лимиты бесплатных облачных минут. Это дает безопасный доступ сборщиков во внутренний периметр инфраструктуры компании без проброса сетевых портов наружу.

## Задача 2: Логи

### Предложенное решение

Для сбора, фильтрации и анализа логов выбран стек на базе компонентов **Vector**, **Elasticsearch** и **Kibana**.

Архитектура взаимодействия компонентов:
1. Микросервисы работают в контейнерах и отправляют все события в стандартные потоки вывода (`stdout` / `stderr`).
2. Агент **Vector** разворачивается на каждом хосте системы (как системный сервис или DaemonSet в Kubernetes). Он перехватывает потоки вывода контейнеров с хоста, парсит JSON-структуру и обогащает записи метаданными (имя хоста, имя контейнера, namespace).
3. При сетевых задержках или сбоях Vector складывает события во встроенный дисковый буфер на локальном сервере.
4. После буферизации Vector передает данные в кластер **Elasticsearch** по протоколу HTTP/HTTPS.
5. Разработчики и инженеры работают с логами через веб-интерфейс **Kibana**.

### Соответствие требованиям

| Требование ТЗ | Реализация в стеке |
|---|---|
| Сбор логов в центральное хранилище со всех хостов | Vector работает на каждом сервере и пересылает события в единый кластер Elasticsearch. |
| Минимальные требования к приложениям, сбор из stdout | Сервисы пишут обычный текст или JSON в `stdout`/`stderr`. Vector читает сокет Docker или системные каталоги `/var/log/containers/` без модификации кода приложений. |
| Гарантированная доставка логов | В Vector настраивается буфер типа `disk` (`buffer.type: disk`). В связке с протоколом подтверждений (acknowledgements) это защищает данные от потери при аварии сети или перезапуске центрального узла. |
| Поиск и фильтрация по записям | Elasticsearch индексирует поля логов. Поддерживаются фильтры по диапазону времени, полям JSON, кодам ответов и полнотекстовый поиск через синтаксис KQL/Lucene. |
| Интерфейс с доступом для разработчиков | Интерфейс Kibana Discover. Разграничение доступа настраивается через Elasticsearch RBAC и Kibana Spaces: разработчики видят только индексы своих приложений. |
| Ссылка на сохранённый поиск | В Kibana реализована функция Saved Search. Кнопка Share формирует постоянную короткую ссылку (Permalinks / Short URL) на конкретную выборку с учетом выставленных фильтров. |

### Обоснование выбора

Vector потребляет минимум оперативной памяти и процессорного времени. Он значительно опережает устаревшие Logstash и Fluentd по производительности. Наличие встроенного механизма буферизации на локальный диск решает задачу гарантированной доставки без необходимости развертывать промежуточные очереди (Apache Kafka или RabbitMQ).

Связка Elasticsearch и Kibana обеспечивает зрелый инструментарий поиска. Разработчики оперативно локализуют инциденты по сохраненным ссылкам без прямого SSH-доступа на серверы.

## Задача 3: Мониторинг

### Предложенное решение

Для сбора, хранения и визуализации метрик системы выбрана связка **Prometheus**, **Node Exporter**, **cAdvisor** и **Grafana**.

Схема взаимодействия компонентов:
1. Системные метрики серверов собирает **Node Exporter**, запущенный на каждом хосте.
2. Метрики потребления ресурсов контейнерами считывает агент **cAdvisor** напрямую из подсистемы cgroups Linux.
3. Специфичные метрики бизнес-логики отдают сами микросервисы через стандартный HTTP-эндпоинт `/metrics` с помощью клиентских библиотек Prometheus.
4. Сервер **Prometheus** по расписанию (pull-модель) опрашивает все агенты и микросервисы, сохраняя метрики в базу временных рядов (TSDB).
5. Визуализация и составление сводных дашбордов выполняются в **Grafana**, подключенной к Prometheus в качестве источника данных (Data Source).

### Соответствие требованиям

| Требование ТЗ | Реализация в стеке |
|---|---|
| Сбор метрик со всех хостов | Prometheus опрашивает агенты по сети. Доступна автоматическая регистрация новых узлов через механизм Service Discovery (DNS, Consul или Kubernetes API). |
| Метрики состояния ресурсов хостов: CPU, RAM, HDD, Network | Node Exporter считывает показатели ядра ОС через procfs и sysfs: загрузку процессора, распределение памяти, заполненность дисковых разделов, сетевые ошибки и трафик. |
| Метрики ресурсов для каждого сервиса: CPU, RAM, HDD, Network | cAdvisor анализирует системные cgroups Docker/containerd. Он собирает метрики CPU Throttling, лимиты памяти (OOM), дисковый I/O и сетевой стек каждого контейнера. |
| Сбор метрик, специфичных для сервиса | В микросервисы внедряются Prometheus Client SDK. Приложения публикуют метрики времени ответа (latency), количества запросов по HTTP-кодам и очередей задач через путь `/metrics`. |
| Пользовательский интерфейс с запросами и агрегацией | Раздел Grafana Explore и встроенный движок PromQL. Поддерживаются агрегатные функции (`sum`, `rate`, `histogram_quantile`, `topk`) и фильтры по меткам. |
| Настраиваемые панели отслеживания состояния | Grafana Dashboards. Платформа дает возможность создавать кастомные виджеты (Time Series, Gauge, Stat, Heatmap), настраивать переменные переключения окружений и шаблонизировать панели. |

### Обоснование выбора

Связка Prometheus и Grafana закрывает полный спектр задач мониторинга микросервисов. Модель сбора методом pull снимает с сервисов нагрузку по пушу метрик: при недоступности мониторинга приложение не накапливает буфер в памяти.

PromQL предоставляет развитый математический аппарат для агрегации данных по меткам сервисов. Grafana служит гибким интерфейсом представления данных, поддерживает разграничение прав доступа и отправку алертов в корпоративные каналы связи.

## Задача 4: Логи * (необязательная)

### Архитектурное решение

В систему добавлен контур сбора и анализа логов на базе стека **Vector + Elasticsearch + Kibana**:
- **Vector.** Запущен в контейнере с пробросом сокета `/var/run/docker.sock`. Агент перехватывает вывод `stdout` и `stderr` контейнеров API Gateway без изменения логики приложений. В конфигурации `vector.toml` через VRL-трансформацию формируется каноничное поле `@timestamp`, а также удаляются служебные метки Docker Compose (`label`) для устранения конфликта динамических схем Elasticsearch.
- **Elasticsearch.** Хранит и индексирует события. База временных рядов работает с включенным модулем безопасности (X-Pack Security). При развертывании через сервисный хук автоматически генерируется учетная запись администратора с полными правами (`superuser`).
- **Kibana.** Опубликована на порту `8081:5601`. Предоставляет аналитический интерфейс для визуализации, поиска по фильтрам KQL и построения графиков интенсивности событий.

### Запуск и проверка

Стек поднимается единой командой:

```bash
docker compose up -d
```

Для проверки поступления логов через API Gateway отправлена серия тестовых HTTP-запросов на эндпоинты `/token` и `/status`.

## Задача 5: Мониторинг * (необязательная)

### Архитектурное решение

В систему внедрен контур сбора и анализа метрик на базе стека **Prometheus** и **Grafana**:
- **Prometheus.** Выполняет периодический опрос (pull-модель) внутренних эндпоинтов сервисов через docker-сеть с интервалом в 5 секунд:
  - `security` -> `http://security:3000/metrics`
  - `uploader` -> `http://uploader:3000/metrics`
  - `storage` (MinIO) -> `http://storage:9000/minio/v2/metrics/cluster`
- **Автоматический Provisioning.** Источник данных Prometheus подключается в Grafana декларативно на этапе запуска контейнера через конфигурационный файл `datasource.yml`. Это избавляет от ручной настройки Data Source в интерфейсе.
- **Маршрутизация портов.** Во избежание сетевого конфликта с Kibana (порт 8081) веб-интерфейс Grafana опубликован на порту `8082:3000`. Логин администратора `admin`, пароль `qwerty123456`.
- **Дашборд распределения нагрузки.** В Grafana создана панель мониторинга из трех аналитических блоков:
  1. *Requests per Second (RPS)* - график динамики входящей интенсивности запросов во времени на базе функции `rate()`.
  2. *Total Requests by Service* - шкала Bar Gauge с суммарным количеством обработанных вызовов.
  3. *Requests Distribution (%)* - круговая диаграмма, наглядно отображающая доли трафика по каждому микросервису.

### Запуск и проверка

Стек мониторинга разворачивается совместно со всеми сервисами проекта:

```bash
docker compose up -d
```
